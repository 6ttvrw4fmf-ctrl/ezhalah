# PLATFORMS WHOSE LIVENESS ORACLE HAS NEVER BEEN SEEN TO RUN IN PRODUCTION
#
# Every platform listed here HAS a source oracle: its run.py passes `verify_gone=` to
# db.prune_unseen(), so a row at grace is re-fetched on its own URL and only an affirmative source
# answer may deactivate it. That is the CANDIDATE_PLUS_DIRECT mechanism, and it is what the liveness
# registry now declares for them.
#
# A MECHANISM IS NOT COVERAGE. The owner's rule, 2026-09-21: "Do not mark a platform as covered
# merely because code exists. Prove the full chain actually runs." Each platform below has produced
# ZERO verdict rows in `ops_stale_inactivation_probe` (oracle = 'prune_unseen.verify_gone') — not a
# single GONE, LIVE or even UNKNOWN. The chain exists and has never been observed to execute. Until
# it has, the honest word for these platforms is UNPROVEN, never "covered", and this file is where
# that is said out loud instead of being inferred from a tier label.
#
# WHY A PLATFORM CAN SIT HERE INNOCENTLY. The probe fires ONLY for a row that reaches grace
# (3 consecutive misses) — a small, stable catalogue re-read in full every run may legitimately
# never produce one, because nothing ever goes missing. So a row in this file is not by itself a
# defect. What it is, is the ABSENCE OF PROOF, and LISTING_LIVENESS.md §9.3 is explicit that a
# checker which has not run proves nothing about its listings: they are UNKNOWN. The danger is the
# other case — an oracle that would throw, 403, or quarantine on its first real candidate, and which
# nothing will discover until the day it is asked to decide whether a listing may be removed.
#
# HOW A PLATFORM LEAVES THIS FILE: produce a real verdict in production. One row in
# ops_stale_inactivation_probe is enough to move it from UNPROVEN to observed:
#
#   select split_part(source_table,'_',1) as platform, verdict, count(*), max(probed_at)
#     from ops_stale_inactivation_probe
#    where oracle = 'prune_unseen.verify_gone'
#    group by 1, 2 order by 1;
#
# TWO THINGS KEEP THIS FILE HONEST, and they are deliberately split by what each can see.
#
#   scripts/verify-oracle-observation-ledger.ts (offline, in `npm test`) judges the REPO half:
#     1. every platform listed here really does wire verify_gone= into prune_unseen — a ledger row
#        for a platform with no oracle is a claim about a mechanism that does not exist;
#     2. every platform listed here is declared CANDIDATE_PLUS_DIRECT or DIRECT_REVISIT — this file
#        records an UNPROVEN mechanism, never a missing one (a platform with no oracle at all
#        belongs in scrapers/absence-only-prune.txt, which is a different gap);
#     3. the count is a RATCHET. It may fall. Raising it is a deliberate, reviewed edit.
#
#   mon_detect_oracle_chain_never_observed() (production, on the detector roster) judges the OTHER
#   half, which no offline check can see: it recomputes the never-observed set from
#   ops_stale_inactivation_probe every sweep and raises per platform. So a row that has since been
#   earned shows up as an alert auto-resolving, and a row missing from this file shows up as an
#   alert naming a platform nobody wrote down. The file cannot quietly disagree with production.
#
# WHY THIS FILE DID NOT EXIST BEFORE (ops_incident #248, #578). db.prune_unseen()'s self-heal wrote
# {missing_count, last_seen_at} and threw the ALIVE verdict away, so `last_verified_alive_at` stayed
# NULL on every oracle-guarded platform no matter how well its oracle ran. The registry then read
# 0% verified everywhere, the CRAWL_PRESENCE_ONLY tier looked correct, and
# mon_detect_liveness_coverage_ramp — whose filter is `strategy in ('DIRECT_REVISIT',
# 'CANDIDATE_PLUS_DIRECT')` — never looked at any of them. Fixing the discarded stamp is what made
# the distinction below measurable at all.
#
